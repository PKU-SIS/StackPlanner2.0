## 为何分阶段通过，串起来仍出问题

分阶段脚本直接构造任务并调用对应 Handler，验证的是特定输入和配置下的阶段行为，不覆盖 Central 的前置记忆召回、实际委派内容及完整上下文传播。预检索与补研脚本显式关闭 thinking，本轮按当前模型配置开启 thinking；此前阶段结果不能等同于当前配置回归。真实流程的补研继承大量材料：258 条既有记录的 preview 合计约 29 万字符，实际首轮输入 210395 tokens，随后约 21–25 万 tokens/次。材料多让累计 token 预算比工具次数更早成为约束。

默认累计 token 预算 200 万，收尾阈值为 70%。本次补研前七次模型调用累计已越过 140 万，按现有中间件逻辑会在下一轮撤掉工具要求收尾。末次返回 DSML 文本且 tool_calls 为空、finish_reason=stop，随后被当成正文处理。收尾切换与异常输出存在明确关联，但尚不能单凭日志断定是服务端还是适配层导致 DSML 泄漏。累计 token 含缓存输入，不等同于同量未缓存费用。

修复链还有一处契约冲突：原文只有 DSML，执行表为空；修复指令既要求保留原执行声明，又要求为每个 gap 输出执行表。修复模型补表后，代码要求执行声明签名必须与空原表完全相同，因此拒收。修复还重新组织了 gap 主题，说明已有输入不足以可靠完成这种“仅修格式”的任务。不是再增加工具次数就能解决。

## 2 次上限从哪来

`sp-memory-recaller` 的 `max_turns=20`，通用工具上限公式为 `max(2,min(cap,(max_turns-6)//6))`，因此算出 2。模型一次提出两个 ls，守卫当场强停。之前的预检索阶段脚本直接委派 report Researcher，没有执行 `sp_recall_memory`；Researcher 已配置 350 步/50 次工具。本轮预检索同样没有触发 2 次上限。

## 建议优先级（本次只分析）

1. 对齐阶段测试与完整流程的 thinking、预算、任务包装和真实输入规模；阶段测试保留价值，但不能替代连接处测试。
2. 补研按指定 gap 提供材料与必要摘要，减少整库 preview 重复注入，先控制输入规模。
3. 区分正常综述、缺失综述与模型工具协议文本；空执行表不要靠无工具模型重建，执行事实由宿主记录保持。
4. 单独处理记忆召回的工具与收尾配置，不再套用报告 Researcher 预算解释。
5. 复用本次现场仅复测补研→Outline，再跑一个原始 query；先不追加批量全流程实验。
