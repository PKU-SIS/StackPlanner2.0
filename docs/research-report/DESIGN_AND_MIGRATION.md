# SP2.0 报告能力：设计基线与迁移清单

- 日期：2026-10-20
- 开发分支：`zx_sp2research`
- 起始基线：`main@1459577db67263286858f9af3eae7d58bcb64679`
- 阶段：第一阶段，设计收束；尚未授权业务代码迁移。

本文将已确认的设计原则与代码迁移边界汇总为可审查基线。标为“建议”的内容尚待规划侧确认，接口名称及文件布局尚未冻结。提交本文不代表以下能力已实现，也不代表已通过真实报告验收。

## 1. 目标与开发依据

在 SP2.0 通用 Harness 上增加高质量报告生成能力，重点实现：

1. Outline 主导材料利用、写作逻辑及证据需求。
2. Researcher 按预检索、正式检索、补充检索的不同任务目的执行检索。
3. Writer 按可直接写作的大纲节点生成文本。
4. Outline 可根据局部写作结果回看并修正规划，不强制逐节点试写。
5. 必要证据无法补齐时向用户主动说明并请求解决，不用缺失说明充当最终报告内容。

开发必须便于合回 main。优先复用现有角色、Skill、工具执行、Artifact、Checkpoint 和人类交互能力；不为报告再建一套独立运行框架。

主要迁移来源：

- `sp2DeepResearch@aaa6b80`：早期 scaffold skill、报告契约等思想和实现。
- 本地旧开发分支 `codex/scope-planning-20261015@5ab780e` 及已有未提交工作：材料、引用、章节交付、诊断等候选资产。
- SP1 `zb_demo_v11@c81444f`：历史职责划分与交互参考，不作为完整 ScaffoldAgent 论文机制的实现证明。

旧开发目录继续保留；迁移以行为和职责为单位，不整包复制旧分支，不把旧测试预期自动作为新设计标准。

## 2. 已确认的权责

| 参与者 | 拥有的决定权与职责 | 边界 |
|---|---|---|
| 用户 | 确定宏观设计与目标，决定实质性范围/口径变更，处理必须由用户解决的问题 | 不被系统内部参数错误反复要求“继续” |
| Central | 宏观任务组织、派发、进度监控、用户交互、收束交付 | 不包办 Outline 的材料与写作规划；不由关键词程序静默覆盖其显式角色选择 |
| Outline | 阅读材料、选择证据、组织树、确定写作逻辑、提出正式检索需求、回看局部写作并修正规划 | 不自行上网检索；不擅改用户硬要求 |
| Researcher | 执行具体证据问题的检索与核验，保留来源、结果、冲突与未解决问题 | 不负责一次性补齐整个报告；不自行决定报告结构 |
| Writer | 将委派节点的内容与论证落实为正文，处理措辞、段落与衔接，反馈明确输入缺陷 | 不承担全局规划、独立选题或网络检索；不擅自补造结论 |
| 程序与工具 | 执行读写、结构与引用身份校验、确定性计算、保存版本、传递状态、执行明确资源边界 | 不用字符串匹配、记录计数等代替证据充分性及内容可比性的语义判断 |

现有角色名称 `reporter` 可继续使用；不为把它称为 Writer 而进行无关重命名。

“工具化”必须转移决定权，而不只是把旧判断函数包一层调用接口。例如：读取指定来源是工具操作，决定这些来源是否足以支持比较是 Outline 的工作。

## 3. 主流程与三类检索

以下是逻辑关系，不是每个任务必须执行固定次数的流水线：

用户需求 → 预检索 → Outline 构思
→〔正式检索 ↔ Outline 修订〕
→ 节点写作 → Outline 按需回看
→〔必要时补充检索、修订节点、重写受影响文本〕
→ 组装、审查与交付。

### 3.1 预检索

- Central 根据用户需求委派 Researcher。
- 获取少量预计会用到的材料，了解对象、主要信息来源、重要口径和问题边界。
- 关注用户硬要求涉及的方向，不要求每个方向的证据已经全部齐备。
- 候选对象和方法可以是暂定方案；不把 Agent 的初步选择升级为不可变用户要求。
- 达到能支持初步构思的程度即可交给 Outline，不以完整指标矩阵作为进入门槛。

### 3.2 正式检索

- Outline 在构思后提出具体证据需求，Central 负责派发，Researcher 执行。
- 这是主要研究工作，可拆为多次委派；正常多次检索不等于失败重试。
- 每次请求说明待回答的问题、相关节点、对象/时间/口径约束，以及已有材料为什么还不够。
- 请求应寻找回答问题所需证据，不要求 Researcher 证明预先认定的结论。
- 结果回到已有规划继续构思，保留当前树、已作决定、未解决问题及材料引用。

### 3.3 补充检索

- Writer 在实际落实节点时发现明确缺陷，例如要求比较 A、B，但只能找到 A 的支持材料。
- Writer 反馈缺陷，Outline 先判断是否已有材料未传到、节点指令有误或确实缺证据。
- 只有确实需要新材料时再由 Central 委派 Researcher。
- 补充结果先用于更新相关写作安排，再交给 Writer 继续。
- 涵盖用户明确要求以及回答这些要求不可缺少的论证；不鼓励 Writer 顺势扩展研究范围。

三类检索复用同一个 Researcher 能力，不新建三个 Agent。参数如何表达阶段由执行方案说明。

## 4. 材料与大纲

### 4.1 材料访问

已确认：

- 材料目录覆盖整个任务，来源与正文可以追溯。
- Outline 获得完整规划视野，并能自主读取和选择已有研究材料。
- 材料排序可以帮助阅读，不能通过静默截断或硬筛选让材料变得不可见。
- 技术输入容量限制仍真实存在；不得伪装成“语义上无需这些材料”。
- Writer 的输入由 Outline 的节点安排锚定；不要求 Writer 再独立遍历全库作研究设计。

建议的实现方式：

- 复用任务现有 Artifact 存储，提供目录、正文读取和来源定位能力。
- 区分“任务全局视野”与“所有原文同时塞进一次调用”：完整树、需求和材料目录可见；正文可按引用读取。
- 读取如因容量必须分段，明确返回未读范围及继续读取方式；不得声称完整读取。
- 来源目录中的相关性描述属于辅助信息，不能由程序评分决定唯一允许使用的来源集合。

### 4.2 可写作节点

树不是简单章节标题列表。一个准备交给 Writer 的写作单元应表达：

- 要回答的问题及其与用户需求的关系；
- 主要论点或分析步骤；
- 证据引用及必要的原文/数据定位；
- 时间、对象、单位、比较口径等必要条件；
- 应体现的结论、边界，以及与其他节点的必要关系。

事实、推导、方法与建议应区分；不要求每个分析结论都逐字出现在单一来源中。能确定执行的计算交由工具完成。

上述为内容要求，不等于每个节点都要填写庞大表单。具体字段与层级粒度在实现方案中给例子，用实际写作效果检验。

树可以按需要扩展；不沿用固定章节数、固定叶子上限等默认规则来压缩必需内容。

## 5. 局部写作与规划修订

已确认：

- 当前取消复杂并行原则，采用顺序推进；不设计多个角色同时修改树的并发协议。
- 顺序推进仍允许“研究一部分—写作一部分—继续规划/研究”，不要求全树证据全部完成后才能第一次写作。
- Outline 可以选择需要写作反馈的节点，不强制每个节点先试写。
- Outline 根据反馈决定保留、扩展、拆分、合并或调整相关节点。
- 对已有正文的影响由 Outline 判断；程序不能根据标题变化自行推断语义影响。

建议的最小版本处理：

- 节点保有稳定身份，草稿记录对应节点与计划版本。
- Outline 修订时指出哪些既有草稿可继续使用、哪些需要重写。
- 工具检查引用身份和版本关系，并保留历史产物，不自动把“版本较旧”解释为“内容一定无效”。
- 未完成影响判断的文本不悄悄进入最终稿；如何标记待处理状态由执行侧给出最简方案。

树的物理分文件可后续按容量需要决定。本轮不把多文件存储、复杂依赖图或并行编辑作为前置工程。

## 6. 证据不足与用户交互

用户硬要求或必要论证缺少证据时，最终处理只能是：

1. 补齐证据并继续；或
2. 主动向用户说明具体问题，获取材料、决定或知情后的明确处理意见。

不能直接在正文放入“缺乏证据”“信息未提供”等文字，就把未完成要求标记为完成；也不能删除相关要求后静默交付。

先由 Agent 判断已有材料是否能解决、是否可以调整自身设定的方法。涉及用户目标、必需对象、范围或实质性口径变化时，由 Central 对用户提出具体问题。

询问应说明卡点和可选择的处理方式，保存已完成的材料与写作，回答后能续接原任务。

合理的不确定性、预测假设与来源冲突仍需如实表达。该规则不能被解释为隐藏不确定性、编造缺失数字或保证不可能取得的数据。

## 7. 报告能力与 Harness 的边界

已确认方向：主要通过 Skill、角色工具和少量必要公共接口实现，保证可合回 main。

建议分层如下，具体目录由执行侧说明，暂不引入新的插件注册框架：

| 层 | 放入的内容 | 不应混入 |
|---|---|---|
| Skill/角色指令 | 三类检索目的、Outline 决策方法、节点写作约定、局部回看策略 | 与实际可调用工具矛盾的能力声明 |
| 报告工具与状态 | 材料读取、树读写、研究/写作请求、草稿与来源绑定、报告组装 | 关键词证据筛选、程序语义充分性裁决 |
| 公共 Harness | 委派、运行状态、Artifact/Checkpoint、用户中断、通用错误传递 | 全局强制每个任务必须生成 Outline/报告 |

报告路径的启用与退出需要显式记录。建议由 Central 根据用户目标选择报告能力，程序校验该选择及所需接口；不新增关键词自动判定器。

Outline 的请求由 Central 派发即可，不必让 Outline 持有 Central 的全部控制动作。请求必须真实返回到调度环节，并在结果返回后恢复规划；仅在最终 JSON 中写一个未被处理的 gaps 字段不算闭环。

工具名、请求结构、恢复调用方式均需执行方案给出；优先复用现有协议，避免新增独立调度循环。

## 8. 恢复、结束与用户可见状态

必须区分：

- 工具参数无效、尚未执行；
- 已执行但只取得部分结果；
- 模型/服务/容量等技术失败；
- 语义上确实缺少完成任务的材料或用户决定；
- 阶段成功与最终交付成功。

程序保留这些客观状态和原始原因；Agent 在允许范围内选择如何继续。参数修正不应误算成另一项任务的失败重试，多次正常研究不应误算成耗尽恢复机会。

不通过提高图步数、隐藏异常或把 incomplete 改成 complete 来制造成功。技术故障可使任务失败，但不能冒充最终报告，也不应无端让用户承担内部参数修正。

研究、规划或章节产物已保存，不等于整个报告已完成。最终报告应能定位当前章节、来源以及用户已批准的范围变化；无活动委派不等于完成。

Central 最终内容审查的详细输入范围，仍按用户决定保留待与合作者讨论。本设计不擅自确定其审查权限，也不增设新的审查 Agent。

## 9. main 中的复用接口与冲突检查

特别需要替换的已发现冲突：

1. main Reporter/通用 reporting skill 仍要求 Writer 自行设计结构、建立事实清单，并允许以缺失说明完成正文。不能与新节点写作约定同时作为最高优先级指令生效。
2. main 的公共角色边界将规划归 Central，且限制子 Agent 委派。新设计要清楚允许 Outline 提交研究/写作请求，同时保留 Central 实际派发职责。
3. main 仍有关键词角色改派；新报告路径不能继承它的静默覆盖。
4. 旧分支的无工具 Outline finalizer、预先覆盖门槛、强制材料筛选、全局报告完成门槛不能整体迁入。

将冲突改成显式、可审查的模式差异，不用不断追加 prompt 优先级来遮盖矛盾，也不批量删除与报告无关的通用功能。

## 11. 建议的交付顺序与验收

这是阶段安排建议，不是当前开发授权。

### D0：设计与迁移边界（当前）

- 交付本文并由用户审阅建议项。
- 执行侧随后提交基于 main 的实现方案：真实接口、修改/新增文件、旧规则替换表，以及一条具体调用示例。
- 只写“新增 skill”不合格；必须说明它实际获得什么工具、如何返回请求、如何续接。

### D1：材料—规划—正式检索闭环

- 预检索产物可保存并由 Outline 自主读取。
- Outline 提出正式检索需求；Central 派发；结果回到同一份规划继续工作。
- 验收一个需要两轮正式检索的例子，能够说明选择了什么资料、为什么还需检索。
- 不要求已实现完整报告，也不能据此声称报告能力完成。

### D2：节点写作—局部反馈—规划修订闭环

- Writer 依据明确节点写作；发现问题可返回。
- Outline 选择性回看、调整节点、请求必要补充检索，并保留不受影响的文本。
- 验收无需每节点试写、无需全部证据到齐才开始写作，且没有复杂并发。

### D3：组装、用户交互与真实验收

- 章节组装、引用可追溯、无法补全时主动询问、恢复和终止状态一致。
- 最终审查的待定设计需在实现对应功能前确认。
- 先分层验证，再小规模真实报告，最后困难报告验收；与非报告任务进行必要回归。

每阶段的代码执行前仍须审阅对应方案。测试验证边界和行为，不能通过改变预期、绕过真实链路、吞掉错误或加入案例专用规则获得“通过”。

## 12. 版本与交付纪律
