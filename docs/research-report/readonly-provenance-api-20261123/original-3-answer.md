结论先说：清单三条不是任何一份资料里的原话，而是报告在结论章（n14《结论：分场景的条件式答案与三个落地检查点》）把前文三个检查点和责任分工“落到人头上”的产物。结论原文自己已声明：“它不引入新的判断标准，只是把上文三个检查点与前述分工落实到具体责任上。”以下逐条拆分资料原意、报告论述依据与建议成分。

1）业务方主责确认
· 报告论述依据：n14 三个检查点之“业务规则是否足够稳定、平台边界是否可接受”，以及 n2/n6 的“效率收益有条件成立”。
· 资料原意：S113（低代码迁移案例，第19行）称低代码在业务信息系统开发、方案探索和早期阶段确有优势，但用户对功能与质量期望上升后，“the effort for customization and optimization of low code applications tends to exceed the effort of classical approaches”。这只支持“适用边界存在、且会随期望上升而反转”。
· 建议/缺证据：“不予承接的场景清单”“试点验收口径”“退出或降级时的业务影响与预算能否由业务侧承担”——无任何资料讨论业务方如何承担预算或如何设定验收口径，属报告的机构安排建议。

2）开发方主责确认
· 报告论述依据：n9《锁定与工程能力缺口》——版本控制、系统性自动化测试、静态代码分析受平台方式限制，资产导出受限。
· 资料原意：S113（第45行）明确“Automation is limited due to the lack of openness of the low code platform. We can neither export information about the UI structure or components, nor can we export a readable format of the activities.”；S13（第23行）称低代码/无代码带来灵活性的同时也需要标准化与控制以管理影子 IT 和技术债，治理应“balances flexibility and standardisation simultaneously rather than treating them as opposing choices”。这支持“可测试性/可导出性是真实约束”和“治理需平衡”。
· 建议/缺证据：“护栏内的实现约定（统一写法）”“变更走自助还是协同通道”“变更后资产与维护责任人如何归属”——资料只描述约束与张力，未给出任何具体实现约定、变更通道或归属规则。

3）运维方主责确认
· 报告论述依据：n14 第三段“省前置、增经常性”，以及 n11《分歧不在“快不快”，而在谁来承担长期成本》。
· 资料原意：S128（苏格兰公共部门评估，第151行）称该方案“has higher recurring costs. This is offset by lower initial development costs, so might be an option if there is a preference to reduce initial capital expenditure at the expense of additional operational (recurring) expenditure.”——支持“经常性成本要算清、这是资本支出与运营支出的取舍”，但未指定由谁承担。S113 第45行支持“数据/逻辑难导出”是退出迁移的真实障碍。
· 建议/缺证据：“升级与发布节奏谁能改动”“能否定期演练”无资料依据；“退出迁移的成本与时间表是否在预算内”也无量化证据——S113 自述仅为“a single use case of a limited size”，未给出迁移成本或工期。

总括：三条中“场景边界会反转”“可导出性/可测试性受限”“经常性成本更高”有原始资料支撑；“三方各自主责什么、验收与退出预算由谁承担、变更走什么通道、是否定期演练”均属报告建议或推断，不是资料结论。以上引自已交付版本 t0004 的已保存证据行，未做独立事实核验。
