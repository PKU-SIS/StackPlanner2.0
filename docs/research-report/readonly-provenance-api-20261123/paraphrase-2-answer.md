### 一、业务方主责确认

**报告论述**：对应检查点一——“业务规则是否足够稳定、平台边界是否可接受”；并承接 n11 的判断：管理者记的是项目预算与上线时间，IT 记的是后续维护账，同一平台评价相反多因记账科目不同。

**已保存来源**
- **S113**（低代码迁移案例研究）：低代码在业务信息系统开发、方案探索与早期阶段确有优势，但用户对功能与质量期望上升后，定制与优化投入往往超过传统方法——n14 保存于第 19 行。
- **S13**（灵活性—标准化张力研究）：治理须同时平衡灵活性与标准化，过度灵活会损害稳定性——n14 第 23 行。
- **S130**（厂商自建市场调查）：2,000 名受访者中 80% 称提升生产力、79% 称降低运营成本、73% 称缩短上市时间；但只问收益感知，样本为员工不少于 1,500 人的五国大型企业。
- **S45**（厂商赞助 TEI 访谈）：采纳前 IT 产能跟不上业务需求，员工自寻变通。

**只是建议的部分**：“不予承接的场景清单”要业务方确认、验收口径由业务方签认、退出或降级的业务影响与预算须由业务侧承担——来源中没有对应主张。

**证据不足**：没有任何已保存来源讨论“验收口径与退出预算应由谁承担”；S130 是感知型收益分布，不含承担主体，也不含可维护性、可迁移性、多年总拥有成本等科目。

### 二、开发方主责确认

**报告论述**：对应检查点二——“资产能否导出、能否支持自动化测试等工程实践”；并承接 n11 的“能不能读懂、能不能测、能不能迁走、两年后改一次需求要付多少”，以及传统工具承担底层逻辑、扩展模块与系统集成的分工事实。

**已保存来源**
- **S113**（第 45 行）：平台开放性不足，无法导出 UI 结构或组件，也无法导出可读的活动格式，自动化迁移因此受限。
- **S156**（Gartner LCAP 报告，第 398–402 行）：市场正从部门自动化的边缘工具转向企业应用交付的核心组件，重心转向融合团队中的专业开发者，并需兼顾集成、可观测性与安全。
- **S165**（开发者生态调查）：中国 17%／全球 10% 使用低代码，为他人构建系统 14%／4%；业务流程自动化中最常见，传统工具更多承担底层逻辑、扩展模块与集成。
- **S153**（24,534 名开发者、194 国调查）：题组重心在 AI 与工具选型，报告自己也说明它不构成低代码态度测验。

**只是建议的部分**：护栏内的实现约定（可测试性、可观测性、扩展口与集成的统一写法）要彼此自洽、变更走自助还是协同通道、资产与维护责任人如何归属——均属建议。

**证据不足**：变更通道归属、护栏的具体颗粒度没有来源；“可观测性／集成”在 S156 中是厂商能力要求，不是责任分配证据；S113 是单用例、小团队的迁移，作者自述自动化受限，外部效度有限。

### 三、运维方主责确认

**报告论述**：对应检查点三——“治理成本与退出迁移成本是否已计入预算”，以及“省前置、增经常性”的净收益表述。

**已保存来源**
- **S128**（苏格兰公共部门成本比较，第 151 行）：该方案经常性成本更高，靠较低的初始开发成本抵消；是否可选取决于是否愿以减少初始资本支出换取更多运营（经常性）支出。
- **S113**（第 45 行）：平台开放性不足直接抬高退出与迁移代价。
- **S13**（第 23 行）：影子 IT、技术债等风险需标准化控制。
- **S29**（采访型证据）：治理缺失时公民开发失控蔓延形成影子 IT，集成失败还会留下无人维护的“僵尸应用”。

**只是建议的部分**：经常性运营成本的口径与承担方、升级与发布节奏谁能改动、数据导出／逻辑读取／集成替换能否定期演练、退出迁移成本与时间表进预算——均属建议。

**证据不足**：没有任何量化净成本、回收期或退出时间表；S128 只给方向性权衡而无具体数字；演练频率与变更权归属无来源；S13 是两家跨国科技公司、57 次访谈的案例研究，其阈值不能直接外推。
