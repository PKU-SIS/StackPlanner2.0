先给结论：这三条“方案责任交接清单”不是资料里的原文，也没有哪份材料直接规定“业务方/开发方/运维方各自确认什么”。它们是报告把结论第4段的三个检查点，加上正文《分歧不在“快不快”，而在谁来承担长期成本》最后一段的分工建议，合并成的一张操作清单；“三方联席评审、任一条不共识就不推进”同样是建议。三条清单本身在结论第5段引出、第6–8段分列，回指的正文段落如下。

一、业务方主责确认
- 对应正文：结论第4段“检查点一：业务规则是否足够稳定、平台边界是否可接受”，以及结论第1段对适用场景的划线；正文依据主要在《分歧…》最后一段“业务侧记的是项目预算与上线时间”。
- 资料：S113《A Use Case and Method for Migrating a Low Code》第19行。
- 资料原意：低代码在业务信息系统开发、方案探索和早期阶段有优势；当用户对功能与质量的期望上升，定制与优化投入往往超过经典方法。
- 区分：把这句话转成“先确认业务规则稳定性和平台边界”，是报告的推导；“不予承接的场景清单”“试点验收口径”“退出/降级的业务影响与预算由业务侧承担”是建议，资料没有直接依据。S130/S45 只支持“业务侧关注上线快、成本低”的感知，不支持责任归属。

三、运维方主责确认
- 对应正文：结论第2段“省前置、增经常性”和结论第4段“检查点三：治理成本与退出迁移成本计入预算”；正文对应《分歧…》开头“开发者接手后的账单：能不能读懂、能不能测、能不能迁走、两年后改一次要付多少”，以及《锁定…》的迁移成本段。
