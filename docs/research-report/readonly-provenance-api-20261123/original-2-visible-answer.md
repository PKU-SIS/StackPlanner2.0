## 一、业务方主责确认

**报告依据**：结论中的检查点一“业务规则是否足够稳定、平台边界是否可接受”；第2章“效率与维护成本不是二选一”、第4章“增长是真实的，但‘影响有多大’要看口径”。

**资料原意**：
- S113（*A Use Case and Method for Migrating a Low Code*）：低代码在业务信息系统开发、方案探索和早期阶段确有优势，但当用户对功能与质量的期望上升后，定制与优化投入往往超过经典方法。
- S128（苏格兰公共部门方案的成本比较）：该选项初始开发成本更低、经常性成本更高；取舍取决于企业是否愿意用后续运营支出去换初期资本支出。

**属于建议**：“不予承接的场景清单”、试点或首版验收口径由业务方主责确认、退出或降级时的业务影响与预算由业务侧承担并接受。资料只支持“适用边界随质量要求上升而收窄”和成本结构，没有提出这种责任清单，也没有提出预算承担的安排。

**证据缺口**：没有材料直接讨论退出或降级时业务影响如何评估、由谁承担预算。这一条不能算作资料结论。

## 二、开发方主责确认

**报告依据**：第9章“锁定与工程能力缺口”、第8章“治理张力”。

**资料原意**：
- S113：该案例中安全与标准视图等部分较易实现，但版本控制、系统性自动化测试、静态代码分析等实践受平台方式限制；同一材料明确写道“自动化受平台开放性限制，既不能导出 UI 结构与组件信息，也不能导出可读的活动格式”。
- S13：基于两家跨国企业 57 次访谈，过度灵活会损害稳定性、过度标准化会扼杀自主性，有效治理需同时动态平衡两端。
- S29：在“恰当护栏”内扩展并不排斥灵活性；预集成不足会产生无人使用、无人维护的“僵尸应用”。

**属于建议**：“护栏内的实现约定（可测试性、可观测性、扩展口与集成的统一写法）”“变更走自助还是协同通道”“变更后资产与维护责任人如何归属”。资料只支持“需要护栏与治理”，并未规定这套约定清单，也未规定变更通道的划分方式。

**证据缺口**：没有资料给出变更通道选择或责任人归属的规则；S29 的存档摘录只覆盖原文第 19–26 行（全文 69 行），是不完整片段。

## 三、运维方主责确认

**报告依据**：结论中“经常性运营成本与退出迁移成本是否已计入预算”；第9章的锁定机制；第11章“分歧不在‘快不快’，而在谁来承担长期成本”。

**资料原意**：
- S128：“该方案经常性成本更高，这由更低的初始开发成本抵消”，若企业更愿意压低初期资本支出、以增加运营（经常性）支出为代价，这可能是一个选项。
- S113：“自动化受平台开放性不足限制”，既无法导出 UI 结构与组件信息，也无法导出可读的活动格式。

**属于建议**：“定期演练数据可导出、逻辑可读取、集成可替换”“升级与发布节奏谁能改动”“退出迁移成本与时间表是否在预算内”。演练这个动作、由此隐含的频次要求，以及把退出成本编入预算，都是我的建议；资料只说明导出能力受限、经常性成本更高。

**证据缺口**：没有资料支持“定期演练”或“退出迁移成本与时间表”的具体口径；也不能由资料推出经常性成本必然高于传统开发（S128 只是单一公共部门方案中某一选项的描述）。

## 整体判断

三条清单的**形式**（三方责任划分、逐条“主责确认”、任一条未达成共识就不推进下一阶段）是报告结论中的建议性构造，没有单一资料直接给出。资料能够支撑的是背后的三个事实性判断：

1. 适用边界随质量要求上升而收窄（S113）；
2. 治理必须在灵活性与标准化之间动态平衡（S13）；
3. 经常性成本与导出受限构成长期成本（S128、S113）。

以上为只读核对结果，报告版本未变动。
