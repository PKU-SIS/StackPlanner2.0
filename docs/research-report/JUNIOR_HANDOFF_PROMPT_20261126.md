# 师妹接手任务书与 Codex 启动 Prompt

## 先看这段：你负责什么

你的目标是把现有报告系统从“功能能跑”推进到“用户用起来顺、复杂改稿也靠谱”。按下面四项推进，先体验和记录问题，再做针对性修改；无需先理解整个仓库才能开始。

1. **自己跑起系统，体验端到端流程**：从零生成一份报告，再连续改稿、刷新、下载，核对页面、正文和版本是否一致。
2. **优化 UI**：解决聊天刷屏、重复交付卡、错误进度面板、状态不清楚等实际体验问题。
3. **拷打多轮对话**：可导入已有成稿，测试增删、精简、重构、补引用、撤销和旧版继续修改，检查是否改准且没有误改其他内容。
4. **优化复杂任务效果**：测试真正需要 Outline 调结构、Researcher 新检索的任务，检查选路、证据使用和局部保持；优先调多轮 prompt，先不增删护栏、不重构公共流程。

**有不懂的先问 Codex。** 请它结合仓库代码解释具体概念、入口、配置和报错，并指出文件位置；不要让它只给抽象建议。访问权限、实验基线或用户目标等 Codex 无法从代码确认的信息，再找负责人核实。

- 仓库：<https://github.com/PKU-SIS/StackPlanner2.0.git>。
- 接手分支：`feature/report-multiturn`，拉取该分支最新 HEAD，不用默认 `main` 或仅拉报告主线 `sp2DeepResearch`。
- 在自己的电脑或开发服务器独立 checkout；代码、环境、模块导入和测试都使用自己的 checkout。

```bash
git clone --branch feature/report-multiturn --single-branch https://github.com/PKU-SIS/StackPlanner2.0.git StackPlanner2.0_multiturn
cd StackPlanner2.0_multiturn
git switch -c feature/report-experience
git log -1 --oneline
git status --short --branch
```

已有 clone 时先保护自己的未提交修改，再 fetch，并从 `origin/feature/report-multiturn` 建自己的分支/worktree。报告数据版本不是代码 Git 分支，不要每轮对话建代码分支。

Git 中包含实现、说明与评测摘要；真实报告快照、运行配置和凭据不随 clone 自动取得。按仓库指南建立自己的环境。需要历史实验基线时，联系负责人取得独立只读副本，不复制整个旧源码目录或 `.env`。不需要到作者原服务器源码目录开发。

## 交给 Codex 的启动 Prompt（可直接复制）

```text
请按 docs/research-report/JUNIOR_HANDOFF_PROMPT_20261126.md 接手现有报告系统，按以下顺序推进：

1. 先读 AGENTS.md 和相关模块指南，核对分支、实际导入路径、配置与启动方式。帮我在自己的 checkout 跑起系统，给我可打开的页面和具体操作步骤。先体验“从零生成报告→连续改稿→刷新→下载”的端到端流程，记录实际现象；不要把导入已有报告当成从零生成测试。

2. 从真实页面体验定位并修复 UI 问题：文件明细刷屏、重复报告卡、局部改稿显示整篇进度、运行或交付状态不清楚。先复现，指出代码位置，小改动修复并验证刷新后的表现。默认页面要清楚显示在做什么、改了哪里、最终报告在哪里。

3. 建立可复现的多轮测试，可用独立导入的已有成稿加快测试。覆盖加一段、删一段、精简三条、局部重构、复用资料补引用、撤销部分要求、选择旧版继续改，以及只读问答。固定每轮 query 和预期保留范围，执行后比较正文、版本与 SHA，记录角色、耗时和 token。不要只以有报告文件或原生交付成功判断改稿正确。

4. 再测试复杂任务：真正新检索补证、增加/删除独立章节，以及调结构后继续局部改稿。检查是否按需调用 Outline/Researcher，新材料是否真正用到正文，其他内容是否保留。有问题优先调条件多轮 prompt，不增删护栏、不加审查 Agent、不改首轮默认流程或公共执行器。每个问题保留复现 case，完成后给我实际 diff、验证结果和剩余问题。

过程中请指导我使用系统：不懂的术语先结合实际代码解释，报错先定位原因再给可执行步骤；需要我手动操作时明确说明操作位置、命令和成功标志。能够独立完成的工作继续做，不要只写计划就结束。信息不足时先完成不依赖它的工作，再指出真正缺少的信息；不要编造配置、接口或测试结果。真实外部调用遵循当前会话授权，不从这份文档推断额外授权。不自行推送、合并、部署或修改他人的运行服务。
```

## 四项任务怎么做、怎么验收

### 1. 自己跑系统与端到端体验

怎么做：先读根 `AGENTS.md`，后端读 `backend/AGENTS.md`，前端读 `frontend/AGENTS.md`，按仓库安装说明准备依赖。让 Codex 根据实际代码核对配置、启动命令和端口；可维护自己的开发实例，不动旧 Demo 和他人的服务。

在新会话里从零生成报告；交付后继续提出两次局部修改，再刷新、重新打开会话、下载最终报告。分别记录初次生成和各轮修改的等待时间、页面现象、报告版本与实际内容。另做普通非报告任务，确认没有被多轮路径误接管。

交付：可复现的运行说明、具体 query、操作记录和问题清单。标明哪些步骤自己体验过、哪些是 Codex 自动执行过、哪些尚未验证；不得仅凭服务启动成功称端到端通过。

### 2. UI 优化

重点查看：大量文件增删列表是否仍铺满聊天；子任务与最终交付是否重复显示报告卡；局部修改是否错误显示整篇写作进度；运行中、失败、取消、交付后状态是否清楚；下载是否对应当前报告，刷新后是否一致。

怎么做：先截图或记录复现步骤，让 Codex 找到组件和数据来源，再逐项修复。默认展示简洁摘要、交付报告和耗时，文件明细与执行细节可展开。UI 需要如实区分版本副本文件变化与正文实际修改范围，不把复制几百个文件说成模型改写了几百处。

交付：修复前后截图/浏览器检查结果、相关前端测试、实际 diff。已有折叠和去重实现要先验证，不重复造一套；普通任务和首轮报告的展示继续正常。

### 3. 多轮对话测试与局部改稿质量

可使用已有成稿，但优先使用程序验证过的原生交付快照，在自己的会话独立导入；不要修改历史版本。如果只有普通 Markdown/Word，先让 Codex 核对系统是否支持导入及版本绑定，不能把复制进目录当成已接受报告。

现成四轮输入在 `docs/research-report/prompt-precision-20261125/REQUESTS.json`，人工可读版是同目录 `CASES.md`。从前两版导入基线后执行第 3–6 轮：新增【交接复核建议】一个自然段；把【迁移演练建议】整块替换为三条；只删除新增段；按准备/执行/交接重构三条。第 1–2 轮是基线说明，不需重跑首轮。

再扩充测试：复用已有材料补引用；撤销一项但保留其他修改；明确选择旧版本后继续编辑；只读问答和整版复用；取消、失败、重复提交和刷新恢复。后几项用已有离线测试/失败注入优先，不为制造失败盲目消耗真实 API。

验收：段落数/条数符合请求；删除确实删除、未重新出现；未修改章节 canonical 保持；原版本文件 SHA 不变；每轮可独立恢复；失败不覆盖旧成功版本；只读和整版复用不派 Researcher/Writer。检查同一章范围外文字，不能只检查其他章。

每轮保留前后正文差异、角色/工具、耗时/token 和结果。评估在执行后进行，预期答案不进入 Agent 上下文，评估器不变成线上护栏。固定请求后保留首次失败，修复复测另建试次，不手工改产物或重跑覆盖失败。

现有 `report_pilot_entry.py` 的 `inspect_turn` 对旧题第 5/6 轮内置只读/ExactReuse 预期，不能直接拿来判本批四轮改稿。`/tmp/sp2_precision_run.py` 是作者临时待实测脚本，不在 Git 中，也不是必须依赖的稳定入口。请把需要的实验入口整理到自己的代码与文档中，复用既有执行和费用观察。

### 4. Outline / Researcher 复杂情况

至少准备以下场景，输入写明需要的新证据、目标位置和保留范围：

| 场景 | 检查重点 |
|---|---|
| 基于已保存材料补引用 | 不要求新检索；引用绑定到对应判断，避免无谓重新研究 |
| 必须新增官方资料的补证 | 明确要求至少两份此前未收录的官方资料；确认实际检索、保存新来源并用于目标正文，不能用旧来源冒充 |
| 增加独立一级章节 | Outline 更新真实章节树；新章节位置正确，未改章节保留 |
| 删除独立章节，再继续改另一处 | 真实结构与最终报告一致；不靠整体回滚删除，其他有效修改仍在 |
| 研究后重新组织已有章节 | 新证据与结构调整协调，说明哪些判断来自资料、哪些是建议，避免整篇无关重写 |

中枢仍负责调度：简单已有章节编辑优先 Writer；独立章节树变化由 Outline 协调；新证据走原生研究路径；GitAgent 可选，不恢复成每轮必调。不用“每轮必须调用某 Agent”当成功标准。

交付：复杂 case 的固定 query、实际角色轨迹、保存来源与正文变化、失败原因及小范围修复。先评估选路和使用效果，引用事实准确率全面修复暂缓；新资料是否支持结论仍需抽查，原生交付不等于事实正确。真正“新证据推翻错误原结论”的完整案例尚未充分验证，可在基本场景稳定后补测，不强行制造矛盾。

## 让 Codex 怎么指导你

可以直接问它：

- “结合当前代码解释 Central、Outline、Researcher、Writer 分别负责什么，指出实现文件。”
- “我该开哪个页面、输入什么、看到什么才算交付成功？请按步骤带我操作。”
- “这条 query 需要哪些角色？实际运行调用了谁？请根据日志核对，不要只讲理论。”
- “这里卡住/报错了，先查日志和调用链，告诉我是配置、UI、模型输出还是程序问题。”
- “这轮虽然交付了，但是否误改其他段落？请比较正文与 canonical SHA。”

要求 Codex 先检查仓库、自己运行可用检查，再给建议；一步一步解释即可，不必每个可逆修改都等待确认。缺少基线、访问权限或真实调用授权时让它说清具体缺什么，继续完成其他工作。Codex 不能代替负责人决定产品目标，也不能保证模型输出和事实一定正确。

## 实验时间与交付建议

大规模或高并发 API 实验建议优先安排在 DeepSeek 波谷时段（**北京时间 / UTC+8**）：周末及中国法定节假日全天；工作日 12:00–14:00、18:00–次日 09:00。日常开发、离线测试、少量串行调试随时进行，无需等待波谷。

这是安排建议，不把历史 100 元讨论变成接手任务的固定额度要求。实验建议记录 token、耗时与费用，批量启动前核对 [官方价格说明](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)（时段于 2026-11-26 核对）。

每阶段交付一份简短记录和可审阅的小范围提交：运行方式、固定 query、实际结果、截图或正文差异、相关回归、用量与剩余问题。原生交付、修改意图、范围保持、事实支持分别判断；不能以一个“成功”状态代替全部质量结论。不只写计划，要留下实际跑过和修过的证据。
