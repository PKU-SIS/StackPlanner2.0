# DeepSeek 真实 case：引用与调用上限验证

使用原 A2A/MCP 请求、当前修改后的 Skills/报告提示词，模型为 `.env` 中的 `deepseek-v4-flash`。本轮在隔离目录调用真实 StackPlanner 图、搜索和抓取工具，未启动应用服务。

## 结果

| 指标 | 原导出 case | 本轮 |
| --- | ---: | ---: |
| 预检索保存材料 | 1 | 4 |
| 全程保存 / 终稿引用来源 | 4 / 4 | 7 / 7 |
| 正文写作节点 | 9 | 12 |
| 节点绑定来源数 | 1 个：4 节；2 个：4 节；3 个：1 节 | 2 个：3 节；3 个：6 节；4 个：2 节；5 个：1 节 |
| 正文引用标记次数 | 52 | 205 |

模型、材料时效和抓取配置与原导出 case 不同，以上是实测对照，不是只改变提示词的严格 A/B 实验。引用数量增加不等于每项事实都已独立核验。

## 暴露的问题

1. **“12 次”是系统内部工具调用上限，不是 API 余额。**预检索实际用了 3 次搜索、6 次逐篇抓取、3 次回读；成功保存 4 篇。两轮 Researcher 都触发 `loop_capped`，其 `summary.md` 变成恢复的工具证据，没有生成预期的连贯、带引用综述。Outline 收尾也发生一次上限中断，恢复后才提交成功。
2. **两次搜索错误发生在 DuckDuckGo 包装层。**返回分别为 `'http_proxy'`、`'ALL_PROXY'`。代码在锁外读取代理变量，锁内临时删除变量；并发搜索存在读/删竞争。第三次搜索成功返回 5 个候选。不是 DeepSeek Search 参数错误，也未观察到 HTTP 402。
3. **节点补充流程确实执行。**Outline 登记 4 个 gap，Central 将它们放进一次 Researcher 委派，新增 3 篇材料；最终 9/12 个正文节点绑定了 3–5 个来源。代价是研究结果受到同一个工具上限约束。
4. **终稿仍有质量建议。**整合审查记录了重复论述、结论标题措辞、内部 material 编号露出和一处无直接来源的修辞表述，均被判为 advisory；本轮通过了交付门禁。

## DeepSeek Search / Fetch 的独立探测

用户提供接口后，分别使用现有 Key 验证：

- Search：HTTP 200，`count=5, need_content=true` 返回 5 条结果，五条都有正文。
- Fetch：HTTP 200，取得 A2A 页面 Markdown。
- 这两个探测不属于本轮报告的检索链路，不能将报告来源增加归因于它们。

本轮报告使用 DuckDuckGo + 已有 direct_fetch。启动前 Jina 连接失败，故仅实验配置切换为 direct_fetch；主配置未改。

**下一步优先方向：把 DeepSeek Search 返回的多篇正文直接登记为报告材料，减少逐篇 Fetch 和重复回读；同时为综述收尾保留执行空间。单纯增加提示词目标，仍会撞上现有调用上限。**
