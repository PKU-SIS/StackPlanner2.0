# 报告流程分段稳定性测试计划

状态：仅设计，尚未改代码或启动真实批次。

## 原则

**拆开原流程，逐阶段验收，再将合格的真实产物交给下游。**保留生产角色、Skills、工具和数据协议，不另搭一条“裸模型生成摘要”的测试流程；不让下游为上游坏产物继续消耗 token。

```text
query.jsonl 的固定 20 条请求
  → 预检索 → 停止、检查、修复、冻结合格产物
  → Outline 初始规划 → 停止、检查、修复、冻结合格大纲
  → 统一补充研究 → 停止、检查、修复、冻结结果
  → Outline 收尾 → 停止、检查、冻结写作树
  → 节点写作 → 检查
  → 原有装配与验收交付
```

## 第一批只做预检索

- query.jsonl 有 100 条请求，中英文各 50 条、22 个主题；固定选 20 条适合研究综述的请求，覆盖不同主题和宽窄任务，包含博物馆 ID 31，保存选样清单。
- 每个样本走原预检索路径，在研究产物成功保存后停止，不启动 Outline、Writer 或终稿审查。
- 检查 summary 是否为正常、连贯、带引用的研究综述；排除 FORCED STOP、Recovered tool evidence、原始工具 JSON 等替代物。
- 自动记录：完成/失败、已保存来源数、正文引用的独立来源数、引用是否指向真实材料、工具次数、错误、耗时与 token；抽看内容相关性。来源数与重复引用次数分开统计。
- 20 条先全部留存结果，失败不偷偷重试到成功；修复后仍在预检索阶段复跑，直到该阶段达到我们认可的稳定程度，再推进下游。

## 下游按原产物继续

| 阶段 | 使用的上游输入 | 本阶段检查什么 |
| --- | --- | --- |
| Outline 初始规划 | 冻结的真实 summary、材料和请求 | 是否生成并接受有效树，material/source 与行号是否正确，用户要求是否有对应章节 |
| 统一补充研究 | 已接受树与其中登记的 gaps | 是否返回正常带引用综述、材料和每个 gap 的真实执行结果 |
| Outline 收尾 | 固定的大纲、补充综述和材料 | 是否能接受修订树、绑定证据、生成写作请求，是否重复提交已关闭 gap |
| Writer 与交付 | 冻结的写作树和真实证据 | 每个正文节点能否写出并接受，是否进入原有装配、验收和交付 |

上游失败记为 blocked_upstream，不运行下游，也不算下游自身失败。后续若发现上游产物有问题，回到那个阶段修复并生成新快照；不混用不匹配的新旧产物。

## 测试入口和边界

- 在原 Handler 接受并保存阶段结果之后提供测试用停止/继续入口，保存真实状态与产物快照；不用强杀进程代替阶段停止，不重新手写下游 prompt 拼出另一条流程。
- 每个样本目录隔离，保存原请求、代码/配置版本、阶段输入输出、日志、指标和失败原因。成功与失败样本都保留。
- 一轮批次冻结模型、提示词、工具和预算，禁止边跑边改；当前提出的总 200/单体 50 尚未实施，需要在正式批次前明确本轮使用的配置并验证实际生效。
- 先用 3 条冒烟验证停止点和记录正确，再跑正式 20 条预检索。第一批不启动后续阶段，服务保持停止；前端整链路回归放到各阶段稳定之后。
